# ADR 0001: Pin the Rust toolchain and let Dependabot move it

- **Status:** Accepted
- **Date:** 2026-10-24

## Context

The toolchain floated in two places: `.mise.toml` asked for `rust = "latest"` and CI installed
`dtolnay/rust-toolchain@stable`. Neither was recorded in the repository. When Rust 1.97 shipped
new clippy lints (`collapsible_match`, `question_mark`), `cargo clippy -- -D warnings` went red with
no code change. The breakage only showed up on the next push, after months of inactivity, in the
middle of unrelated work.

Dependencies had the same shape: `Cargo.lock` pins them, but nothing proposed updates, so drift
built up silently until someone ran `cargo update` by hand.

## Options considered

1. **Keep floating, add a scheduled CI run on stable.** Breakage surfaces on a schedule instead of
   on push, but `main` is still red until someone fixes it, and dependencies still drift.
2. **A custom scheduled workflow that runs `cargo update` / bumps the toolchain and opens a PR.**
   This re-implements Dependabot. PRs opened with the default `GITHUB_TOKEN` do not trigger CI, so it
   would also need a PAT or GitHub App just to get the PR checked.
3. **Pin the toolchain in one file and let Dependabot propose every update as a PR.** Each update
   is an isolated, reviewable change, and CI on that PR is the compatibility check.

## Decision

Option 3.

- `rust-toolchain.toml` is the single source of truth for the toolchain, with `clippy` and
  `rustfmt`. rustup honours it locally and in the cargo-dist release jobs.
- CI installs from that file via `actions-rust-lang/setup-rust-toolchain`, which also handles
  caching and sets `CARGO_BUILD_WARNINGS=deny`, so rustc warnings fail CI as well as clippy ones.
- `.mise.toml` reads the version from `rust-toolchain.toml`
  (`idiomatic_version_file_enable_tools = ["rust"]`) instead of declaring its own. A mise-declared
  version would set `RUSTUP_TOOLCHAIN` and override the file.
- `.github/dependabot.yml` checks weekly:
  - `rust-toolchain`: one PR per new stable release.
  - `cargo`: minor and patch bumps grouped into one PR, majors individually, with a 7-day cooldown
    so a freshly published (possibly compromised) crate is never picked up on day one.
  - `github-actions`: grouped, 7-day cooldown, excluding `release.yml`. That file is generated by
    cargo-dist, which rejects hand edits; it is updated by bumping `cargo-dist-version` and
    re-running `dist init`.

## Consequences

- A new Rust release turns up as a PR. If it brings new lints, that PR is red and gets fixed there;
  `main` stays green.
- Release binaries are built with the pinned toolchain, so releases are reproducible.
- Someone has to merge the weekly PRs. For a low-traffic repo that's a few minutes a week, and
  skipping a week costs nothing because Dependabot rebases its own PRs.
- `rust-version = "1.75"` (MSRV) in `Cargo.toml` is separate from the development toolchain and is
  still not tested in CI. Verifying it, or raising it to what is actually tested, is a follow-up.
- An optional weekly canary job on `beta` would give about six weeks' warning of new lints. It is
  deferred until this setup has run for a while.
